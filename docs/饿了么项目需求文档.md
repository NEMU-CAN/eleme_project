## 1 项目概述

本项目是一套供普通用户点餐、供商家经营门店的外卖系统。普通用户注册登录后，可以浏览店铺和菜品、维护收货地址、管理购物车、下单并完成模拟支付。商家通过开店申请获得经营入口，在商家中心处理订单、菜品和店铺资料。

本文档记录当前代码对应的角色、流程、功能边界、数据规则和验收条件。需求发生变化时，先更新文档，再改代码和测试。

## 2 产品目标

系统应跑通用户点餐和商家经营两条流程，并保证两端读取同一份业务数据。

1. 用户能够完成从浏览店铺到提交订单和支付的完整流程。
2. 商家能够完成开店申请，并管理自己的订单、菜品和门店资料。
3. 用户、地址、购物车、订单、库存和商家数据通过后端接口持久化。
4. 页面适配桌面和常见手机宽度，并分别处理加载中、无数据和加载失败状态。

## 3 用户角色和权限

| 角色 | 编码 | 主要权限 |
| --- | ---: | --- |
| 普通用户 | 0 | 浏览店铺和菜品，管理个人资料、地址和购物车，创建及查看自己的订单 |
| 商家 | 1 | 具备普通登录能力，可查看自己的店铺，管理所属店铺的订单、菜品和资料 |
| 管理员 | 2 | 保留系统管理权限，可进入商家相关管理页面；具体后台管理功能不在本期范围内 |

权限边界：

- 未登录用户可以注册、登录、浏览营业店铺、查看店铺详情和在售菜品。
- 个人资料、地址、购物车、订单和商家管理接口必须登录后访问。
- 普通用户不能修改其他用户的数据，也不能访问商家管理能力。
- 商家只能管理归属于自己的店铺、菜品和订单。
- 后端必须以登录令牌识别用户身份，不能仅依赖前端传入的用户编号。

## 4 核心业务流程

### 4.1 用户点餐流程

1. 用户注册普通账户或使用已有账户登录。
2. 用户在首页选择分类、搜索店铺或使用筛选条件查找商家。
3. 用户进入店铺详情页，查看菜品、价格和剩余库存。
4. 用户将有库存且已上架的菜品加入购物车。
5. 用户进入结算页并选择有效收货地址。
6. 系统根据购物车内容、菜品价格、起送价和配送费创建待支付订单。
7. 用户在支付页选择支付方式并完成模拟支付。
8. 用户可在订单页查看订单状态和详情。

### 4.2 商家经营流程

1. 普通用户从“我的”页面进入“我要开店”。
2. 用户填写门店名称、地址、介绍、图片、分类、起送价和配送费等资料并提交。
3. 开店成功后，账户获得商家身份并可进入商家中心。
4. 商家在菜品管理中新增或编辑菜品，并控制菜品上下架。
5. 用户下单后，商家可在订单管理中查看订单详情并确认订单完成。
6. 商家可在店铺资料页修改门店信息和营业状态。

## 5 用户端功能需求

### 5.1 注册和登录

| 编号 | 需求 |
| --- | --- |
| AUTH 001 | 注册页只注册普通用户，不提供商家角色选择。 |
| AUTH 002 | 注册时必须填写手机号、密码、昵称和性别，头像可通过本地图片选择器上传。 |
| AUTH 003 | 手机号必须唯一；重复手机号注册时应显示后端返回的明确错误。 |
| AUTH 004 | 登录时使用手机号和密码，登录成功后保存令牌并加载当前用户数据。 |
| AUTH 005 | 登录失效或接口返回未授权时，应清理本地登录状态并引导用户重新登录。 |
| AUTH 006 | 退出登录前必须显示二次确认；用户确认后调用退出接口并清理本地状态。 |

### 5.2 首页和店铺浏览

| 编号 | 需求 |
| --- | --- |
| HOME 001 | 首页顶部显示当前常用地址；没有地址时提示用户新增地址。 |

| HOME 003 | 用户可以按口味分类筛选店铺，分类数据从后端获取。 |

| HOME 005 | 店铺列表展示门店图片、名称、起送价、配送费、状态及菜品预览。 |

## 7 数据和业务规则

### 7.1 数据实体

| 实体 | 关键内容 | 关系 |
| --- | --- | --- |
| 用户 | 手机号、密码摘要、昵称、性别、头像、角色、账户状态 | 一个用户拥有多个地址、订单和购物车条目 |
| 商家 | 名称、地址、介绍、图片、分类、价格配置、状态 | 一个商家拥有多个菜品和订单 |
| 菜品 | 名称、介绍、图片、价格、库存、状态 | 每个菜品属于一个商家 |
| 购物车 | 用户、商家、菜品、数量 | 同一用户和菜品应合并数量 |
| 收货地址 | 联系人、性别、电话、详细地址 | 每个地址属于一个用户 |
| 订单 | 用户、商家、时间、金额、地址快照、状态 | 一个订单包含多个订单明细 |
| 订单明细 | 菜品、数量、成交单价 | 每条明细属于一个订单 |
| 口味分类 | 分类名称 | 商家关联一个口味分类 |

### 7.2 枚举编码

- 性别：保密为0，男为1，女为2。
- 用户角色：普通用户为0，商家为1，管理员为2。
- 所有枚举接口字段使用数字编码传输，前后端不得传入编码范围外的值。
- 后端遇到非法枚举值时返回业务错误；前端向用户显示可理解的提示，不直接展示技术异常文本。

### 7.3 金额和库存规则

- 所有金额使用十进制定点数处理，页面显示保留两位小数。
- 订单商品金额由后端按下单时的菜品价格计算。
- 配送费计入订单总额，是否满足起送价按商品金额判断。
- 下单时库存必须充足，扣减库存的过程应保证原子性，不能出现负库存。
- 订单明细应保存成交单价，避免菜品后续改价影响历史订单金额。

## 8 接口需求

前端通过 `/api` 前缀访问后端。注册、登录、店铺浏览、菜品浏览和分类查询是公开接口；其余请求须在 `Authorization` 请求头中携带 Bearer Token。

| 模块 | 方法和路径 | 用途 |
| --- | --- | --- |
| 认证 | `POST /api/login` | 登录 |
| 认证 | `DELETE /api/logout` | 退出登录并使当前令牌失效 |
| 用户 | `POST /api/users` | 注册普通用户 |
| 用户 | `GET /api/users` | 获取当前用户 |
| 用户 | `PUT /api/users` | 更新当前用户资料 |
| 用户 | `DELETE /api/users` | 删除当前账户 |
| 商家 | `GET /api/businesses` | 查询店铺列表 |
| 商家 | `GET /api/businesses/{id}` | 查询店铺详情 |
| 商家 | `GET /api/businesses/mine` | 查询当前账户的门店 |
| 商家 | `POST /api/businesses` | 创建门店 |
| 商家 | `PUT /api/businesses/{id}` | 更新门店资料 |
| 商家 | `PUT /api/businesses/{id}/status` | 更新门店状态 |
| 菜品 | `GET /api/foods` | 查询菜品列表 |
| 菜品 | `GET /api/foods/{id}` | 查询菜品详情 |
| 菜品 | `POST /api/foods` | 新增菜品 |
| 菜品 | `PUT /api/foods/{id}` | 更新菜品 |
| 菜品 | `PUT /api/foods/{id}/status` | 更新菜品状态 |
| 分类 | `GET /api/tastes` | 查询口味分类 |
| 购物车 | `GET /api/cart/items` | 查询当前用户购物车 |
| 购物车 | `POST /api/cart/items` | 加入购物车 |
| 购物车 | `PUT /api/cart/items/{foodId}` | 修改商品数量 |
| 购物车 | `DELETE /api/cart/items/{foodId}` | 删除商品 |
| 购物车 | `DELETE /api/cart/items` | 清空全部或指定商家的购物车 |
| 地址 | `GET /api/addresses` | 查询当前用户地址 |
| 地址 | `GET /api/addresses/{id}` | 查询地址详情 |
| 地址 | `POST /api/addresses` | 新增地址 |
| 地址 | `PUT /api/addresses/{id}` | 修改地址 |
| 地址 | `DELETE /api/addresses/{id}` | 删除地址 |
| 订单 | `POST /api/orders` | 创建订单 |
| 订单 | `GET /api/orders` | 分页查询用户或商家订单 |
| 订单 | `GET /api/orders/{id}` | 查询订单详情 |
| 订单 | `PUT /api/orders/{id}/status` | 更新订单状态 |

接口响应使用统一结构，包含业务状态码、提示信息和数据。参数校验失败、未登录、无权限、资源不存在和业务冲突分别返回对应的 HTTP 状态；错误信息应便于前端展示或转换。

## 10 非功能需求

### 10.1 安全

- 密码不得以明文保存或返回给前端。
- JWT 应具有有效期；退出登录、删除账户或重新登录后，旧令牌应失效。
- 后端必须验证资源归属和角色权限，前端隐藏按钮不能替代权限校验。
- 日志和错误响应不得输出密码、完整令牌等敏感信息。

### 10.2 易用性

- 所有提交操作应提供进行中状态，防止重复点击。
- 成功和失败操作应给出明确反馈。
- 列表应处理加载中、空数据和加载失败三种状态。
- 删除账户、删除地址、清空购物车和退出登录等重要操作必须二次确认。
- 表单应在提交前完成必填项、长度、数值范围和格式校验。

### 10.3 兼容性与性能

- 前端应兼容主流 Chromium 浏览器，并适配常见手机宽度。
- 首屏不应一次加载所有订单和大量历史数据；订单接口使用分页参数。
- 图片应控制体积并提供加载失败占位图，避免大尺寸图片阻塞页面。
- 常规列表查询在正常开发环境下应尽量在2秒内返回可展示结果。

### 10.4 可维护性

- 前端使用 Vue 3、TypeScript、Vue Router 和 Vite。
- 后端使用 Java 21、Spring Boot、MyBatis 和 MySQL。
- 状态编码统一由枚举维护，禁止在业务代码中散落含义不明的数字常量。
- 前后端字段、接口路径和状态含义发生变化时，应同步更新本文档和接口文档。

## 11 验收标准

### 11.1 用户主流程验收

1. 新手机号可以完成注册和登录，重复手机号注册失败并显示原因。
2. 用户可以浏览营业店铺及有库存的在售菜品。
3. 用户可以新增地址，将菜品加入购物车并创建订单。
4. 库存不足、未达到起送价或没有收货地址时不能成功下单。
5. 用户可以完成模拟支付，并在订单列表中看到状态变化。
6. 用户只能看到自己的地址、购物车和订单。

### 11.2 商家主流程验收

1. 普通用户可以从“我要开店”提交完整门店资料。
2. 开店成功后可以进入商家中心并看到自己的门店。
3. 商家可以新增和编辑菜品，并切换上下架状态。
4. 用户端能看到商家已上架菜品、价格和正确库存。
5. 商家可以查看本店订单详情，并将已支付订单确认完成。
6. 商家可以修改店铺资料和营业状态，保存后其他相关页面同步显示新数据。

### 11.3 账户和异常验收

1. 退出登录前出现二次确认，确认退出后受保护页面不可继续访问。
2. 用户可以选择新头像并保存，未选择新头像时原头像不丢失。
3. 删除账户前出现二次确认，删除后旧令牌不能继续使用。
4. 非法枚举值、无效参数、越权访问和不存在的资源均返回明确错误。
5. 前端不直接向用户显示“参数格式错误或枚举值非法”等缺少上下文的技术提示。

## 12 本期不包含的功能

当前版本不包含下列功能。后续若要开发，需先补充需求和接口设计：

- 真实支付宝或微信支付接入及退款。
- 配送员角色、实时配送轨迹和预计送达时间。
- 客服消息持久化、客服坐席、历史消息和消息推送。
- 发票申请、抬头管理和电子发票下载。
- 菜品物理删除和历史数据恢复。
- 用户评价、商家评分、优惠券、满减和会员体系。
- 商家审核、资质上传、结算和财务报表。
- 独立的管理员后台页面。

## 13 变更管理

每次需求变更都要记录原因，以及受影响的页面、接口、数据结构和验收项。角色权限、订单状态、库存扣减、账户删除或金额计算发生变化时，还要检查后端校验和旧数据是否兼容。测试结果按本文档的需求编号归档。

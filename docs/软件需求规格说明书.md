## 1 项目目标、涉众分析与范围界定

### 1.1 项目目标

本项目为小学期软件工程综合实践项目，目标分为业务产品目标与实训教学目标两个层面。

**业务产品目标**：构建轻量级外卖服务平台（仿饿了么），面向顾客完成外卖核心业务闭环：顾客可完成账号注册与登录、浏览商家与食品、维护收货地址、管理购物车、创建订单与查询订单。商家与食品作为系统供给侧数据预置提供，支撑顾客侧完整业务流程的演示与联调，并为后续需求变更迭代预留扩展空间。

**实训教学目标**：落地前后端分离架构与 RESTful 接口规范，贯彻 TDD 测试优先开发流程；验证架构对需求变更的扩展能力，训练小组协作开发、Git 版本管理与交叉验收能力，完成软件工程全流程实践。

### 1.2 涉众分析

| 序号 | 涉众分类 | 代表角色 | 核心诉求 | 核心关注点 |
|------|----------|----------|----------|------------|
| 1 | 终端用户——顾客 | 平台注册用户 | 便捷浏览商家与食品、快速下单、订单可查询、账号信息准确 | 操作流程简洁、商品信息准确、金额一致、异常提示友好 |
| 2 | 供给方——商家/店铺 | 预置商家数据 | 店铺与食品信息准确完整，供顾客浏览与下单 | 店铺分类清晰、食品信息齐全、图片可正常展示 |
| 3 | 项目开发组 | 后端/前端开发人员 | 接口契约清晰、业务分层明确、架构易扩展、便于联调与测试 | RESTful 接口规范、代码解耦、统一返回格式、TDD 可落地 |
| 4 | 交叉验收组 | 其他实训小组 | 接口语义明确、业务逻辑可验证、Bug 可复现 | 接口命名规范、返回格式统一、测试点清晰、验收标准可量化 |
| 5 | 项目指导方 | 授课教师 | 完整的软件工程过程产出、可验证的架构能力与 TDD 落地效果 | 文档完整性、Git 提交过程、测试覆盖率、需求变更适配能力 |

### 1.3 目标用户特征

**顾客用户**：普通互联网用户，具备外卖平台使用经验，无专业技术背景。使用场景涵盖浏览选购、加入购物车、下单与查看订单。对系统的核心期望为操作简单、响应流畅、金额准确、状态清晰。

**商家/店铺数据方**：本期商家以预置数据形式存在，由初始化脚本提供店铺、食品及分类信息，供顾客侧浏览与下单使用，不参与运行期交互。

**开发与验收人员**：具备 Java 后端与 Vue 前端开发基础，了解接口测试方法，依据本文档开展接口联调与交叉验收。对系统的核心期望为分层清晰、接口定义明确、业务规则无歧义、数据口径一致。

### 1.4 项目约束条件

- **时间约束**：开发周期共 3 周（2026-08-31 至 2026-09-20），分三个阶段交付，分别为基础功能开发、需求变更迭代、功能完善与验收。
- **技术约束**：后端采用 SpringBoot + MyBatis + Lombok，前端采用 Vue3 + TypeScript + Vite（组件库 Element Plus），数据库使用 MySQL；接口遵循 RESTful 规范。
- **流程约束**：按任务书要求执行 TDD 测试优先开发，核心接口测试覆盖率达 100%；Git 全程持续提交，禁止期末集中上传代码；需求变更须留存记录与回归测试证据。
- **协作约束**：前后端接口契约前置定义并维护于仓库 docs 目录；最终交付须通过跨小组交叉验收。

### 1.5 范围界定

**本期范围（阶段1 基础功能）**：
- 用户：注册、登录、查询个人资料。
- 商家/食品浏览：商家列表（按点餐分类过滤）、商家详情、某商家食品列表。
- 收货地址：按用户增删改查。
- 购物车：查询、加入（同用户同商家同食品累加）、修改数量、删除单条、按条件删除。
- 订单：从购物车按商家创建订单、订单列表、订单详情。

**不在本期范围**：商家注册与经营后台、店铺营业状态管理、食品分类、食品库存字段与扣减、食品的商家端维护、真实支付对接、配送流程、平台运营后台及管理员角色。以上按任务书安排于阶段2 需求变更迭代中实施。


## 2 业务领域概念模型

### 2.1 概述

本系统现阶段为顾客消费侧业务系统：供给方（商家与食品）以初始化数据方式预置，顾客完成浏览、加购、下单与查询。系统核心围绕"用户—商家/食品—收货地址—购物车—订单"构建业务闭环，业务概念均从业务视角定义，不涉及数据库表结构等具体技术实现。

### 2.2 核心业务概念明细

| 概念ID | 概念名称 | 业务描述 | 核心业务属性 | 关联概念 | 核心业务规则 |
|--------|----------|----------|--------------|----------|--------------|
| BC-01 | 用户（顾客） | 平台的消费侧主体，账号作为唯一标识 | 账号、密码、姓名、性别、头像、删除标记 | 收货地址、购物车项、订单 | 1. 账号全局唯一；2. 账号密码校验通过方可登录；3. 删除态用户禁止登录 |
| BC-02 | 商家/店铺 | 食品的供给载体，本期以预置数据存在 | 编号、名称、地址、介绍、图片、点餐分类、起送价、配送费、备注 | 食品、订单 | 1. 商家按点餐分类区分；2. 本期无营业状态字段与商家后台 |
| BC-03 | 食品 | 店铺内售卖的菜品，是交易的最小单元 | 编号、名称、介绍、图片、价格、备注 | 商家、购物车项、订单条目 | 1. 一个食品归属一个商家；2. 本期无独立分类与库存字段；3. 订单金额以下单时价格为准 |
| BC-04 | 收货地址 | 顾客下单使用的配送地址 | 联系人、联系电话、详细地址、性别 | 用户、订单 | 1. 地址归属某用户；2. 仅本人可操作；3. 下单须提供属于本人的地址 |
| BC-05 | 购物车 | 顾客选购商品的临时载体 | 食品、商家、用户、数量 | 用户、食品、商家 | 1. 同用户同商家同食品仅一条记录，重复加入累加数量；2. 数量不小于 1；3. 创建订单时按商家读取 |
| BC-06 | 订单 | 顾客提交的交易凭证 | 编号、用户、商家、下单时间、总金额、收货地址、订单状态 | 用户、商家、收货地址、订单条目 | 1. 一个订单归属一个用户、一个商家、一个地址；2. 总金额由服务端计算；3. 状态为 0 未支付、1 已支付 |
| BC-07 | 订单条目 | 订单中的购买明细 | 订单、食品、数量 | 订单、食品 | 1. 明细随订单生成；2. 下单后食品价格变更不影响既有订单总额 |

### 2.3 业务概念关联关系

- **用户与收货地址**：一对多关系。一个用户可维护多个地址；一个地址仅归属一个用户。
- **用户与购物车项**：一对多关系。一个用户可有多个购物车项；一个购物车项仅归属一个用户。
- **购物车项与食品**：多对一关系。一个购物车项对应一个食品；一个食品可被多个用户加入购物车。
- **商家与食品**：一对多关系。一个商家有多件食品；一件食品仅归属一个商家。
- **用户与订单**：一对多关系。一个用户可有多个订单；一个订单仅归属一个用户。
- **商家与订单**：一对多关系。一个商家可产生多个订单；一个订单对应一个商家。
- **订单与收货地址**：多对一关系。一个订单使用一个收货地址。
- **订单与订单条目**：一对多关系。一个订单包含多个条目；条目记录食品与数量。


## 3 业务过程建模

### 3.1 概述

本章基于第 2 章业务概念，对系统的核心业务流程进行建模，描述业务流转规则、对象状态变化及参与方交互过程。本系统不包含真实第三方支付对接与配送流程，支付与订单状态以模拟方式表达。

### 3.2 顾客浏览与购物车流程

顾客登录后浏览商家列表，可按点餐分类过滤；进入商家查看食品并加入购物车。购物车以"用户+商家"维度组织，同一用户在同一商家加入相同食品时数量累加。顾客可查看购物车、修改数量、删除条目，并按商家进入结算。

### 3.3 下单与订单生成流程

顾客从购物车发起下单，流程如下：

1. 顾客选择目标商家与本人收货地址，提交下单请求；
2. 系统执行校验：
   - 购物车非空校验；
   - 该商家下购物车条目存在性校验；
   - 收货地址归属当前用户校验；
3. 校验通过后，系统按食品价格与数量生成订单明细，明细合计作为订单总额；
4. 生成订单记录，订单初始状态为 0（未支付）；
5. 顾客在订单列表与详情中查询订单。

任一校验失败，系统拒绝下单并返回对应错误信息；历史订单演示数据以状态 1（已支付）预置，供"我的订单"页面展示。

### 3.4 账号生命周期流程

顾客注册时填写账号、密码、姓名、性别等信息，系统校验必填项与账号唯一性后创建用户。登录时校验账号与密码，成功返回本人资料（不含密码）；账号不存在或密码错误统一返回登录失败；删除态用户禁止登录。

### 3.5 订单金额一致性与明细说明

订单总额由服务端计算，不信任前端传入金额：下单时服务端读取所选商家的购物车条目，逐条以食品当前价格与数量生成明细，明细合计为订单总额。由此保证订单总额与明细一致，且下单后食品价格变更不影响既有订单。


## 4 功能性需求

### 4.1 执行者分析

**顾客**：顾客为平台的主要购买方，指在平台注册并通过平台浏览商家与食品、选购商品和创建订单的用户。顾客核心操作包括：注册、登录及查询本人资料；浏览商家列表与详情、浏览食品；加入购物车、查询与修改购物车项；创建订单并查询本人订单。

**商家/店铺数据方**：本期商家作为系统供给侧数据预置提供，不涉及登录与经营操作，无商家侧用例。

### 4.2 用户账户功能

| 功能 | 描述 | 关键业务规则 |
|------|------|--------------|
| 用户注册 | 创建顾客账号 | 账号为业务编码主键且全局唯一；密码、姓名非空；性别 1 男 0 女；新用户删除标记为正常态；账号重复返回资源冲突 |
| 用户登录 | 账号密码校验登录 | 校验通过返回本人资料（不含密码）；账号不存在或密码错误统一返回登录失败；删除态用户禁止登录 |
| 个人信息查询 | 按账号查询本人资料 | 返回账号、姓名、性别、头像、删除标记等；不返回密码字段 |

### 4.3 商家与食品浏览功能

| 功能 | 描述 | 关键业务规则 |
|------|------|--------------|
| 商家列表 | 查询商家列表 | 支持按点餐分类过滤；返回名称、地址、介绍、图片、分类、起送价、配送费、备注 |
| 商家详情 | 按商家编号查询 | 商家不存在返回资源不存在 |
| 商家食品列表 | 查询某商家下食品 | 返回食品编号、名称、介绍、图片、价格、备注；无食品返回空列表 |

> 说明：本期商家与食品为只读浏览，无商家后台维护、无食品分类筛选、无库存展示。

| 订单详情 | 查询本人订单详情 | 返回订单主信息、商家、收货地址与明细；非本人或不存在返回资源不存在 |
| 订单状态 | 0 未支付、1 已支付 | 下单初始为 0；本期无支付与状态流转接口，历史订单以初始化数据提供已支付记录 |


## 5 非功能性需求

### 5.1 系统架构要求

系统采用前后端分离架构：

- **前端**：Vue3 + TypeScript + Vite，组件库 Element Plus，负责页面渲染与用户交互。
- **后端**：SpringBoot + MyBatis + Lombok，采用分层结构（entity、vo、result、controller、service、mapper），负责接口提供、业务逻辑与数据持久化。
- **数据库**：MySQL，存储用户、商家、食品、购物车、收货地址、订单与订单明细等业务数据。
- **运行环境**：课程开发与测试环境，前后端本地运行，通过 HTTP 接口联调。

### 5.2 接口规范

**接口风格**：接口统一以资源为中心，资源名称使用复数名词，通过 HTTP 方法表达操作：GET 查询、POST 创建、PUT/PATCH 更新、DELETE 删除。资源标识放入路径，过滤条件使用查询参数。

**路径与数据格式**：接口统一使用 /api 前缀；请求与响应使用 UTF-8 编码的 JSON；时间格式为 yyyy-MM-dd HH:mm:ss；金额以元计，保留两位小数。

**统一响应与错误处理**：后端统一返回体结构为 { code, msg, data }，code=1 表示成功；错误信息给出可理解、可定位的业务原因。错误码定义如下：

| 业务码 | 含义 |
|--------|------|
| 40001 | 请求参数错误（字段校验失败） |
| 40101 | 账号或密码错误 |
| 40401 | 资源不存在 |
| 40901 | 业务冲突 |

HTTP 状态码：200/201 表示成功与资源创建，400/401/404/409 对应上述业务错误。

### 5.3 安全与数据要求

- **数据归属校验**：收货地址、购物车、订单均须校验归属当前用户，越权访问视为资源不存在，归属校验在服务层完成。
- **输入校验**：对必填项、长度、范围、枚举取值及资源存在性进行校验。
- **金额安全**：涉及金额计算使用精确数值类型，订单总额由服务端计算，不信任前端传入金额。
- **敏感信息保护**：任何接口不得返回密码字段；密码当前按约定存储，其存储改进列为阶段2事项。
- **数据一致性**：创建订单等关键写操作应保证数据一致，订单总额与明细保持一致。

### 5.4 性能指标

以课程统一测试环境和演示规模数据为前提：

| 编号 | 指标 | 验收口径 | 目标 |
|------|------|----------|------|
| 1 | 查询响应 | 商家、食品、购物车、订单等常规查询接口 | 95% 的请求在 2 秒内完成 |
| 2 | 写操作响应 | 创建订单、加入购物车、地址增删改等 | 95% 的请求在 3 秒内完成 |
| 3 | 数据一致 | 订单创建后总额与明细一致 | 无金额不一致或重复有效订单 |

### 5.5 界面要求

前端页面覆盖"首页—商家列表—商家详情—确认订单—支付—订单—个人中心"完整链路，核心下单路径连续，返回路径明确；登录、注册与 404 页面已补齐。界面风格统一参考主流外卖应用交互：金额、时间等统一格式化；加载与提交显示处理中状态并防止重复提交；空数据、无权限、资源不存在等场景均提供可理解反馈。

### 5.6 范围一致性说明

系统本期仅包含顾客侧业务用例；支付与配送为演示/模拟口径；商家端、食品分类、库存、营业状态、JWT 鉴权及平台运营后台不属于本期范围，将在阶段2 需求变更迭代中规划实施。本文档所有需求描述均与本项目数据库结构与接口实现保持一致。
